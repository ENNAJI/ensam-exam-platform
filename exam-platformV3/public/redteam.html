VULN-001 Secret JWT hardcodé et faible
CVSS 9.1 — CRITIQUE A02:2021 Cryptographic Failures Phase 2 — Weaponization
Qu'est-ce que c'est ?
Le JSON Web Token (JWT) est un standard pour transmettre des identités entre client et serveur. Sa sécurité repose entièrement sur le secret utilisé pour le signer. Ici, le secret ensam-ctf-2024 est codé en dur dans le code source et exposé en clair dans le fichier backup/jwt_config.txt accessible via FTP.

Impact : Toute personne connaissant ce secret peut forger un token JWT avec n'importe quel rôle (admin), court-circuitant toute la couche d'authentification.

Contre-mesure : Utiliser un secret aléatoire de 256+ bits stocké dans une variable d'environnement non versionnée (.env dans .gitignore).
$ python3 -c "import jwt; print(jwt.encode({'id':1,'role':'admin','nom':'hacker'}, 'ensam-ctf-2024', algorithm='HS256'))" # → eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6MSwicm9sZSI6ImFkbWluIn0.xxx
VULN-002 Endpoint /api/debug sans authentification
CVSS 9.8 — CRITIQUE A05:2021 Security Misconfiguration Phase 5 — C2
Qu'est-ce que c'est ?
Un endpoint de débogage a été laissé actif sur le serveur de staging. Il retourne en clair : le secret JWT, la liste complète des utilisateurs avec leurs hash de mots de passe, la configuration du serveur, le nombre de sessions actives, la version Node.js et la plateforme OS.

Impact : Exposition totale des informations internes du serveur sans aucune authentification. Combiné avec VULN-001, cela permet la compromission complète de l'authentification.

Contre-mesure : Désactiver ou protéger les endpoints de debug en production. Utiliser des variables d'environnement pour conditionner leur activation (if (process.env.NODE_ENV !== 'production')).
$ curl http://[IP]:3003/api/debug { "jwt_secret": "ensam-ctf-2024", "users": [{"nom":"admin","role":"admin","motDePasse":"$2b$10$..."}], "activeSessions": 3 }
VULN-003 IDOR — Accès aux réponses correctes
CVSS 8.6 — ÉLEVÉ A01:2021 Broken Access Control Phase 3 — Exploitation
Qu'est-ce qu'un IDOR ?
Un IDOR (Insecure Direct Object Reference) est une vulnérabilité de contrôle d'accès où un attaquant peut accéder à des ressources qui ne lui appartiennent pas en modifiant simplement un identifiant dans l'URL. Le serveur utilise l'identifiant fourni directement pour accéder aux données sans vérifier que le demandeur est bien le propriétaire.

Impact : N'importe qui possédant un sessionId (ou devinant celui d'un autre) peut obtenir les bonnes réponses de l'examen, rendant la tromperie triviale.

Contre-mesure : Toujours vérifier côté serveur que session.etudiantId === req.user.id avant de retourner des données sensibles.
$ curl http://[IP]:3003/api/examen/answers/VOTRE_SESSION_ID # Aucune authentification requise — retourne toutes les bonnes réponses { "answers": { "qcm": [{"id":1,"reponse_correcte":"B"}, ...], "redaction": [{"id":1,"reponse_modele":"..."}] } }
VULN-004 Mass Assignment — Override de note via _note
CVSS 9.1 — CRITIQUE A04:2021 Insecure Design Phase 7 — Actions
Qu'est-ce que le Mass Assignment ?
Le Mass Assignment survient quand un serveur accepte et traite des paramètres non prévus envoyés par le client. Ici, l'endpoint /api/examen/submit traite un paramètre _note non documenté qui remplace directement la note calculée automatiquement.

Impact : Un étudiant peut se donner la note qu'il veut (0 à 20) en ajoutant simplement "_note": 20 dans sa requête de soumission. Invisible dans l'interface normale.

Contre-mesure : Utiliser une liste blanche stricte des paramètres acceptés. Ne jamais laisser le client influencer la logique de calcul métier (notes, prix, permissions).
$ curl -X POST http://[IP]:3003/api/examen/submit \ -H "Content-Type: application/json" \ -d '{"sessionId":"...","reponses":{},"_note":20}' # → {"noteSur20":20,"_overridden":true}

VULN-015SSRF — Webhook sans validation
